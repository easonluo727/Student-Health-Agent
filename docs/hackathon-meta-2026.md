## 3. 创新方向：从"选计划"到"看完病"的全程真实价格

一句话 pitch：**美国人看病之前不知道要花多少钱，看完以后也不知道账单对不对。我们用保险公司被迫公开、却几乎没人用的协商价数据，让 agent 在三个时刻都给出某一个具体医生的真实数字。**

```
看病前（已有）          看病时（路线图第 1 步）        看病后（新）
选哪个计划？            去哪个医生？                  账单对不对？
Arena 对比        →     附近网络内的具体医生，    →   拍下账单 / EOB，
                        每位都按他自己的协商价算       逐行对照这位医生的协商价
```

三个阶段用的是同一套资产：保单库 + 按 NPI 的价格库 + 计算器。新加的部分都在已有的地基上。

### 3.1 核心（必须做）：附近的具体医生 + 每位医生的真实价格

就是路线图第 1 步（详见 `docs/improvements.md`）。

- 用户说"我喉咙痛，在 UCLA 附近，愿意开 20 分钟车"。
- Python：找计划网络里合适专科的医生 → 用 NPPES 查名字和地址 → 算距离 → 用 `allowed.component(..., npi=...)` 取**这位医生**的协商价 → 计算器算用户自付。
- Agent（Muse Spark）：结合用户的优先级，推荐 1–5 位并解释为什么。
- **为什么算创新**：同一个计划里，同一项服务在不同医生那里的价格可以差好几倍。以前普通人看不到这个差别，这次是第一次直接告诉用户。

### 3.2 亮点（建议做）：账单审核（Bill / EOB checker）

用户拍一张医疗账单或保险公司寄来的 EOB（Explanation of Benefits）：

1. **Muse Spark（多模态）读图**：抽出医生名或 NPI、日期、每一行的 CPT 编号、收费金额、保险已付、要你付的。输出用 JSON schema 约束，模型只做抽取。
2. **Python 核对**：
   - 这位医生在你的网络里，这个编号的协商价是多少（价格库）；
   - 按你的计划，这一项你应该付多少（计算器）；
   - 差额在哪：收费超过协商价、网络内医生却向你收差价（balance billing）、同一项重复收费、急诊被当成网络外收费（No Surprises Act 管的情况）。
3. **Agent 解释**，并起草一封给保险公司或医院账单部门的申诉信（短文本，数字全部来自 Python）。

**为什么这是最好的亮点**：
- 正好是 "make something possible that wasn't before"：普通人以前没法知道"医院跟保险公司谈好的价"是多少，也就没法发现账单多收了。
- 用到了 Muse 的多模态能力，而且是**必要**的（账单都是纸或 PDF 照片），不是为了用而用。
- 有钱的故事：帮用户省钱或拿回钱，Startup 赛道评委会喜欢。
- 跟我们的原则一致：模型只读和解释，钱全由 Python 算。

**限制，要如实说**：价格库只有 41 个编号、只有洛杉矶的医生；账单上不在库里的编号要回答"没有数据"，不能猜。Demo 用编出来的样例账单，不用真实病人的数据。

### 3.3 可选（有时间再做，按性价比排）

- **拍保险卡认计划**：拍卡 → Muse 读出保险公司和计划名 → Python 匹配保单库。工作量小，开场体验好，可以当作 demo 的第一步。
- **上传 PDF 当场抽取新计划**（`improvements.md` P1 第 1 条）：用 Muse Spark 读整份 SBC，每一行都附原文引用；**Python 检查引用是否真的出现在 PDF 文字里**（pdftotext），对不上的不用。故事是"保单库可以自己扩展到全美，而且每个数字都能查证"。比 3.2 难，风险也大。
- **用开源权重模型微调抽取模型**（Modal）：只用人工核对过的数据训练（项目规则）。10 天内不建议做。

### 3.3.1 微调模型（2026-10-26 评估）

**可行，但只适合一个窄任务，而且要先有评测集。**

- **要训练的模型：Muse Glimmer**（2026-10-26 查文档：https://dev.meta.ai/docs/muse-glimmer）。Meta 的开源权重模型，30B 参数，能读文字和图片，从 Muse Spark 蒸馏而来，Apache 2.0 许可。官方的训练文档（https://dev.meta.ai/docs/muse-glimmer/post-training）推荐先用 SFT（给"输入 → 正确输出"的例子），工具是 Axolotl 或 TRL，第一次实验用 QLoRA（显存最省）。30B 用 QLoRA 大约需要一张 80 GB 的 GPU（A100 / H100），在 Modal 上训几个小时约 $10–40。Fireworks、Unsloth 是它的发布合作方，可能有更省事的托管训练，要确认。Muse Spark 本身走 API，不能训练。
- **训练什么**：
  - **保单抽取（SBC → 行）不适合**：现在 9 个计划共 818 行，`verified` 一列全是空的。项目规则禁止用没人工核对过的抽取结果训练；就算全部核对完，9 份文档也太少。
  - **账单 / EOB 抽取（建议）**：用程序生成样例账单（随机医生、编号、金额，渲染成 PDF 或图片），**标签在生成时就已知，是准确的**，不需要人工核对，想要几千张都可以。任务很窄：读出每一行的编号和金额，输出 JSON。
- **怎么展示**：同一个评测集上比较三个模型：Muse Spark、没训练的小开源模型、训练后的小模型，看抽取准确率、速度和成本。故事是："账单含个人健康信息，训练后的小模型可以跑在我们自己的服务器上，数据不出门，准确率接近大模型。"
- **注意**：
  - 生成的账单和真实账单有差距，要留几张真实格式的账单做测试，并隐去个人信息。
  - 用 Muse Spark 的输出当训练数据（蒸馏）之前，要先看 API 条款是否允许。用程序生成的标签就没有这个问题。
  - **训多模态，输入是账单图片**（2026-10-26 定）。不走"先 OCR 再训文字模型"。所以生成器要做出各种样子的图片：多种版式、扫描件效果、手机拍照（倾斜、模糊、阴影、反光）、多页，否则模型只学会读我们自己的模板。训练前先测没训练的 Glimmer 在评测集上的分数，作为基线。Meta 官方训练文档确认支持带图片的 SFT（Axolotl 有 vision QLoRA 配置，视觉部分冻住只训语言层）。
  - **在哪训**（2026-10-26 查）：Fireworks 的 Glimmer 30B SFT 到 11-30 免费，不用信用卡，不用申请比赛额度（https://fireworks.ai/pricing）。**2026-10-27 实测可以**：在网页上传 20 张假账单图片（JSONL，图片用 base64 的 `image_url`），任务跑完，余额 $0 没扣钱；Render Samples 显示每张图变成 726 个视觉 token 进了模型，只有 assistant 的 JSON 计入 loss。余额为 0 时不能创建 API key，只能在网页上操作。训完的模型只能用专用部署（H100 约 $8/小时），demo 时再开。不行就用 Unsloth（30B QLoRA 带图片约需 24 GB 显存，有免费的 Kaggle 笔记本，https://unsloth.ai/docs/models/muse-glimmer/train）或 Modal。
- **时间**：等 3.1 和 3.2 都能用了再做（大约 11-01 之后）。评测集要先做，因为它同时也是 3.2 的测试。训练失败不影响 demo。

### 3.4 不建议做的

- 用 Muse Image 生成图片、用 SAM 3.1 做分割：硬塞进来评委看得出，跟我们的问题无关。
- 打电话核实医生是否接收新病人（ghost network 问题）：很有价值，但 10 天内做不完，留到以后。

## 5. 风险和要先确认的事

1. **API 兼容性（2026-10-26 查了文档，已解决）**：Meta Model API（https://dev.meta.ai/docs）原生支持 **Responses API**，`server.py` 不用改，只换环境变量：`LLM_BASE_URL=https://api.meta.ai/v1`、`LLM_API_KEY=<MODEL_API_KEY>`、`LLM_MODEL=muse-spark-1.3`（复杂任务可换 `muse-wonder-1.0`）。上下文 1M token，支持并行工具调用和流式工具参数。2026-10-26 实测：文字、工具调用、流式都通；但 Meta 会偶尔对它确实提供的模型回 404 `model_not_found`（`muse-spark-1.3` 简单请求约 1/6，线上 Railway 一轮对话 6 次错 5 次；`muse-spark-1.2` 带工具的 agent 请求也会出），同一请求重试就好。同日晚些时候发现某个模型会整段时间（几分钟以上）都这样，`muse-wonder-1.0` 也会，而同一时间别的模型正常；失败的响应带 `proxy-status: http_request_error`，是 Meta 网关连不上该模型的服务器，不是限流。所以 `llm_client.py` 改成遇到这种 404 就换 `LLM_FALLBACK_MODELS` 里的下一个模型，整串试两轮。
1b. **网页搜索用 Meta 自带的 `web_search` 工具（文档：https://dev.meta.ai/docs/search-grounding）**：在 Responses API 的 `tools` 里加 `{"type": "web_search"}`，可以和我们自己的函数工具一起用（我们的工具名不能用 `browser.search`、`browser.open`、`browser.find`）。**搜不搜由模型决定**，正好符合"每一步都是 agent 的选择"。加 `include: ["web_search_call.results"]` 能拿到每个来源的标题、链接和摘录（模型看到的文字），回答里有 `url_citation` 标出哪句话来自哪个链接；可以传 `user_location`（洛杉矶）。不用自己接 Tavily 之类的搜索服务。**不做网页截图**（2026-10-26 定）。限制：多步、多来源的复杂研究不太可靠，要拆成小问题；只给摘录不给全文，要核对整段原文得自己再抓网页；文档没写返回结果里有没有搜索词，拿到 key 后确认。另外文档里还有 Computer use（路线图第 3 步可能用得上）。
2. **模型能力**：Muse Spark、Muse Wonder 各自擅长什么，要等开幕资料或 workshop 确认，本文没有核实。要测的有：工具调用稳不稳、看图读账单准不准。
3. **健康数据隐私**：demo 和测试只用编出来的账单。真实用户上传的账单含个人健康信息，正式上线前要想清楚存哪里、存多久（现在对话保存一天）。
4. **正式规则**：开赛时发布。要看：能不能用比赛前就写好的代码（多数黑客松要求说明哪些是比赛期间做的）、提交要什么（视频、仓库、线上地址）、是否必须用 Meta 模型做主模型。
5. **备用方案**：保留现在的 Kimi 配置，Meta API 出问题时 demo 还能跑。
