# Product
这是一个能够进行保险判别的产品，主要干两件事情：
1. **费用预测**：针对用户现有的保险和可能的疾病，预测用户要支付的价格。
2. **保险推荐（Insurance Arena）**：根据用户的病情和需求，从不同的保险里**找到最适合用户的那一个**，并说明原因。

**目标用户：全美所有人，覆盖所有保险人群**：雇主保险、个人 / marketplace 保险、学生保险，以及正在选保险的人。目前的数据只覆盖洛杉矶的第一批计划，会逐步扩大。

**产品的本质是 matching**：把用户的需求，和我们提前掌握的保险数据、价格数据做匹配，最后告诉用户该怎么选、要花多少钱。


# 产品形式
1. **主界面是一个对话窗**（类似 Hark）。用户直接用自然语言提问，agent 在对话里回答、追问、展示结果。
2. **问卷辅助 LLM 做判断**：我们提供一个**问题库**，LLM 根据用户的问题，从问题库里挑出它需要知道的信息，以问卷的形式在对话中发给用户填写。
3. **三个信息来源一起做 matching**：问卷（来自用户），加上两个我们自己搭建的数据库（保单信息、allowed amount）。**客观的数字和排序由 Python 计算；比较、判断、怎么回复用户由 LLM 决定。**

```
用户在对话窗里提问
   ↓
LLM 判断：需要知道哪些信息？从问题库里挑题，组成问卷
   ↓
用户填写问卷 ──────────────────────┐
                                   ↓
         ┌───────── matching ─────────┐
         │ ① 问卷：用户的信息和需求    │
         │ ② 保单信息数据库            │  → Python 计算数字 → LLM 判断并回复 → 对话中展示结果 / dashboard
         │ ③ allowed amount 数据库     │
         └────────────────────────────┘
   ↓ 用户问到数据库里没有的保险公司
搜索：现场查找这家公司的信息，判断是否合适
```


# 三个信息来源

## ① 问卷（来自用户）
- **问卷的本质是问题库**：我们不预先做好“选保险问卷”“看病问卷”这类固定问卷，而是提供一个问题库，由 LLM 根据用户的问题挑出需要的题目。用哪些题，取决于用户问了什么。
- 问题库写在 HINT 里，注入 LLM 的提示词。LLM 只能从问题库里选题，不能自己现场编问题，这对能力较弱的开源模型更可靠。
- 示例：

| 用户说的话 | LLM 的判断 |
| --- | --- |
| “请问你有什么功能？” | 不需要问卷，直接回答 |
| “这是我的 UC SHIP，你觉得这个保险怎么样？” | 挑选病情、常用药、就医习惯等题目 |
| “你推荐什么别的商业保险吗？” | 挑选预算、各项需求的权重等题目 |

- **每一轮对话都可以发问卷**，不只是第一句话之后。用户已经说过的信息，在问卷里自动填好，并标明“来自你的描述，请确认”。
- 设计要求：
  - **问题库要足够完整**，包含所有需要的信息。
  - **每道题都要能对应到两个数据库的查询条件**，否则收集到的信息用不上。
  - 每道题都要有“不知道”或“跳过”选项。用户选“不知道”时，用区间或多种情况分别计算，不能卡住不动。
  - 选项尽量由后端根据数据生成。例如“在哪里看病”的选项，来自这个保险计划的网络层级。
  - 问卷里收集**用户对各个因素的权重**（例如更在意保费还是看病时的自付、能不能接受大病时的高额自付），LLM 根据这些权重做判断。
  - 答案按字段结构化地交回给 agent，并记录“来自用户问卷”。用户填写的数字直接交给 Python 计算器，模型不能转述或修改。
- 问题库的具体内容、权重的设置方式，之后单独讨论。

## ② 保单信息数据库
回答“**保险怎么分担费用**”。保存除了 allowed amount 以外，保单 PDF 里的**所有信息**。
- 内容：保费、deductible、copay、coinsurance、out-of-pocket max、网络层级、转诊 / 预授权、限制条件、不保项目。
- 收录范围：目标是全美各类保险计划。现有数据从洛杉矶开始：UC SHIP（作为一个普通计划收录）和 Covered California 的计划。
- 来源：团队从官方渠道收集的保单 PDF（Schedule of Benefits / SBC、保费表）、用户上传的保单。离线收集资料时可以使用 Tavily 等工具。
- 处理：由 LLM 读取 PDF，提取成统一的格式（规则 JSON v2，分计划层和规则层两层），再经过程序验证和人工复核。
- 每个数字都附有出处（保单页码、原文摘录）。
- 不计算保费补贴。

## ③ Allowed amount 数据库（价格）
回答“**这项服务值多少钱**”。
- 来源：保险公司依法公开的 **In-Network Rate Machine-Readable Files（MRF）**（Transparency in Coverage）。
- 流程：
  1. 用户描述 → 候选的 CPT / HCPCS 服务代码，不能确定时通过问卷澄清
  2. 确定保险公司、具体计划、医生（NPI）、地区、日期、计费场景
  3. 获取 MRF
  4. 用流式 JSON 解析筛选出适用的协商价
  5. 存进 SQLite
- 注意：
  - 只有服务代码和保险公司名称，确定不了某位医生的具体价格。
  - 公开的协商价，也不保证等于最终理赔时的 allowed amount。
- 价格分三种状态：`verified_rate`（查到的）、`estimated_rate`（估算的）、`rate_unavailable`（查不到）。查不到具体医生的价格时，给出地区的低 / 中 / 高区间，并标明是估算以及来源。

**两个数据库要能对上**：同一个计划在保单信息数据库和 MRF 里的编号不同，需要一张对照表，确保“规则”和“价格”来自同一个计划。

### 辅助对照表
- 服务对照：用户的通俗说法 → 统一服务名称（`service_key`）→ CPT 代码
- 计划对照：我们的 `plan_id` → MRF 里的计划编号
- 医生信息：NPI（政府公开的 NPPES）


# 搜索
- **现状**：2026-10-20 删掉了原来的 Playwright 搜索 worker（按关键词到保险公司官网找背景信息，结果不参与算钱，也从没部署过）。现在用户问到库里没有的计划或保险公司时，agent 直接说明查不到。
- **新的搜索还没定**。候选方向：
  1. **找保单**：用户说出库里没有的计划名，就去网上找它的官方 SBC PDF，交给抽取流程（`scripts/policy/extract_sbc.py`），生成这次对话专用的临时计划，然后就能算钱。和"上传 PDF"共用一条抽取流程。
  2. **找医生**："我的医生在不在这个计划的网内、协商价多少"，查 3.1 GB 的价格库（按 NPI），不用上网。
- MRF 没法现场查：保险公司只提供巨大的压缩 JSON 文件，没有查询接口，必须像现在这样提前切出需要的部分。


# Agent 与代码的分工
原则：**LLM 负责把非结构化的东西变成结构化的，以及做判断和回复；Python 负责客观的数字计算和排序。**

| 交给 LLM | 写死在 Python 里 | 无法完全自动化 |
| --- | --- | --- |
| 从问题库里挑题、组成问卷 | 费用计算（deductible → coinsurance → OOP max） | 协商价 ≠ 最终的 allowed amount（只能估算） |
| 读保单 PDF、提取 benefit | 数据库查询，按各项指标排序 | 保证理赔结果（需人工核实） |
| 理解用户 request、追问 | 数据校验（schema + 规则） | 用户未来的病情（只能按场景假设） |
| 用户描述 → 候选服务代码 | “不懂就问”的强制检查（`guards.py`） | |
| 根据用户的权重比较计划、做出推荐 | | |
| 搜索时提取关键信息、判断是否合适 | | |
| 解释结果、引用原文 | | |

Agent 作为调度员，把能力做成 tools：发问卷、查保单信息、查价格、算钱、排序、搜索、查原文。每个 tool 内部尽量确定、可测试。


# Agent Output

## 情况一：费用预测
最终给出一个非常直接的数字，并用表格呈现中间计算过程中每一步的费用。
- 输入：保单信息（数据库 ②）+ 价格（数据库 ③）+ 用户在问卷里填写的信息（如剩余 deductible）
- 输出：预计自付金额、计算依据、保单页码、价格来源、假设和不确定性
- 拿不到确定的价格时，输出**区间**（低 / 中 / 高三个 allowed amount 各算一遍），并标明是估算以及来源。
- 条款有歧义时保留 `needs_review`，不编造确定的金额。


## 情况二：Insurance Arena（找到最适合的保险）
数据来源：
1. **保单信息数据库**
2. **allowed amount 数据库**
3. **用户的问卷**（病情、常用药、就医习惯、预算、各项需求的权重）
4. **搜索**：数据库里没有的保险公司，现场搜索并判断是否合适

**Python 准备客观事实**：每个计划在各个场景下的年度总花费（年保费 + 预期自付，受 OOP max 封顶），以及各项指标的排序。场景包括：
- 健康年（体检 + 少量门诊）
- 用户的预期使用（根据问卷里的病情推出，用户可调整）
- 意外大病（急诊 + 住院，衡量最坏情况）

**LLM 根据用户的权重做判断**，推荐最适合的计划并说明原因。推荐和比较的结果会生成一个 dashboard，以可视化的形式展示；用户可以在对话里针对 dashboard 上的内容继续提问。

不使用综合评分（如 8.5/10），用"省多少钱 + 有什么风险"说话。各计划差距很小时，直接告诉用户"差不多，看其他因素"。非价格因素（网络大小、转诊 / 预授权、理赔口碑）一并展示。


# 前端形式：对话窗为主
- **对话窗是主界面**（类似 Hark）。
- **问卷**：在对话中以表单卡片的形式出现，支持单选、多选、填空，每题都有“不知道”选项。具体的交互参考另一个产品，用 REA 研究后确定；只借鉴交互思路，界面由我们自己设计。
- **确认卡片**：只在 agent 有猜测时出现。计算要用到的服务、网络、金额里，只要有一项是 agent 从聊天里推断的，就先展示出来，用户确认后才计算；全部来自问卷的，直接计算。
- **结果展示**：
  - 简单的问题，直接在对话里回答：数字 + 计算过程表格。
  - Insurance Arena 在对话旁边的面板里展示 dashboard，从结论到细节逐层展开：
    1. 推荐结论（一句话说明原因 + 被排除的计划）
    2. 场景对比图（每个计划的花费区间，可调整假设）
    3. 对比表（2–4 个计划并排，和用户病情相关的行高亮）
    4. 细节和出处（每个数字对应保单页码或价格来源）
- **搜索进度**：以实时文字显示在对话里。
- 对话中的要求：
  - 用户可以修改假设（如"我一年看 10 次专科"），结果随之更新。
  - 点击 dashboard 上的条目，agent 直接解释该条。
  - agent 不自己算数，所有数字来自后端 tools，保证和 dashboard 一致。
  - 不给医疗建议、不保证理赔，必要时引导用户找保险公司核实。
- 只做桌面 web 端，不考虑手机端。

参考资料：`docs/research/hark-interaction-patterns.md`

### 架构与部署
```
Railway 上的一个服务 agent-api
 └─ FastAPI agent 服务
     ├─ 静态导出的 Next.js 前端（对话窗 + 问卷卡片 + dashboard 面板），在 /
     ├─ API（SSE，协议见 docs/frontend-protocol.md），在 /api
     ├─ agent 流程（调用 LLM，供应商由环境变量配置）
     ├─ 匹配和计算：plan_db.py、calculate_cost.py、guards.py
     └─ 只读数据：保单信息数据库（data/plans/policy.sqlite）+ allowed amount 价格库（rates.sqlite，3.1 GB，Railway 磁盘卷）
```
- 模型供应商是配置项（`workflow/llm_client.py`），每个比赛按要求换。
- 数据都是只读的，跟着代码一起部署，不需要 Supabase。
- **report JSON 是 dashboard 的唯一数据来源**：后端生成和更新它，前端渲染它，agent 读取它。

技术细节见 `AGENTS.md` 和 `db/README.md`。


# Demo 流程
**演示人物**（只是一个例子）：26 岁的 UCLA 博士生，美国公民，刚满 26 岁、不能再用父母的保险，需要自己选保险。轻度哮喘（日常用吸入剂，一年看 2 次专科），一次流感去 urgent care，一次打球扭伤脚踝去急诊、拍 X 光。

1. 用户：“这是我的 UC SHIP，你觉得这个保险怎么样？”
2. agent 发问卷，用户填写病情和就医习惯。
3. agent 评价 UC SHIP：各场景下要花多少钱、有什么风险（价格来自 MRF 数据库）。
4. 用户：“你推荐什么别的商业保险吗？”
5. agent 再发问卷，用户填写预算和各项需求的权重。
6. agent 从数据库里匹配，推荐最适合的计划，并展示 dashboard。
7. 用户问一家**数据库里没有**的保险公司 → agent 说明查不到（新的搜索做好以后再改这一步）。


# Criteria to success
1. the correctness of the info generated
2. the quality of recommendation
    1. in-person verification
    2. 对几组计划请懂保险的人人工排序，看推荐结果是否一致
3. the scope of insurance being considered (how many companies and plans being considered)
4. **matching 的质量**：问卷挑的题对不对（该问的问、不该问的不问），收集到的信息能不能用于两个数据库的查询
5. **搜索**：新的搜索定下来以后再定标准
