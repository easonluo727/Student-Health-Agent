- 主攻赛道：**Health and Wellbeing**。评审关注：明确的患者需求、负责任地处理健康信息、实用易懂的结果、可衡量的改善。

## 2. 核心原则

1. **LLM 把非结构化内容变成结构化数据；Python 负责判断和所有计算。** 数字永远不由模型生成。
2. **靠数据库，不靠模型记忆。** 保险信息每年都变，又要求数字精确，所以知识放在可追溯的保险目录里，模型负责理解和查找。训练不能替代数据库（参见法律 AI 产品的做法，以及 Mata v. Avianca 案中 AI 编造判例的教训）。
3. **为能力较弱的模型设计。** 运行时模型只做选择题和填空题：从固定选项里选、填参数、写短文字。难的工作交给 Python 规则、外部工具和离线流程。
4. **不懂就问，由程序强制执行**（`workflow/guards.py`）。判断不了时一律去问用户，不靠 prompt。
5. **每个值都有出处，并且可以验证。** 原文摘录必须一字不差，由程序核对。

## 3. 总体架构

```
              离线：建数据库（主要的 AMD 计算负载）
┌──────────────────────────────────────────────────────────┐
│ ① 政府结构化数据 ─ Python 直接转换 ──────────┐            │
│ ② 深度搜索找到的保单 ─┐                     │            │
│ ③ 用户上传的保单 ─────┼→ AMD 模型提取 → 验证 → 人工复核 ─┼→ 保险目录（v2 JSON）
│ ④ 人工录入（种子、标准答案）──────────────────┘            │
└──────────────────────────────────────────────────────────┘
                                ↑ 找到新计划后补充进去
              在线：用户提问时                   │
┌──────────────────────────────────────────────────────────┐
│ agent（AMD 模型）→ 先查目录 → 没有的话启动深度搜索 ───────┘
│        ↓
│ Python 计算 → report JSON → 前端 dashboard + 对话
└──────────────────────────────────────────────────────────┘
```

## 4. 保险目录（数据库）

- 格式：**规则 JSON v2**，分计划层和规则层两层，见 issue #1。网络层级和额度（deductible、OOP max、最高赔付）由每个计划自己声明。
- 存储：比赛期间每个计划存一个文件 `policies/<plan_id>.json`，以后再改成数据库。
- 每个计划的状态：已发现 → 已拿到文件 → 已提取 → 程序验证通过 → 人工复核通过 → **已发布**。只有已发布的计划才参与对比；其他计划在界面上标明“资料不完整”或“待复核”。
- 每条记录都带有：来源网址、抓取时间、提取方式、保单年度、是否经过人工复核。每年保单更新后重新处理。

### 数据来源

| 来源 | 适用对象 | 方式 | 状态 |
| --- | --- | --- | --- |
| ① 政府数据 | ACA 市场计划 | CMS Exchange Public Use Files：计划属性、费用分担、按年龄的保费。用 Python 直接转换，不用 LLM | ✅ 2026 年数据已公开。⚠️ **加州（Covered California）不在其中**，演示时用某个 HealthCare.gov 州来展示。⚠️ F-1 学生是否有资格购买 ACA 计划，需要查证 |
| ② 深度搜索 | 学校保险（SHIP）、留学生商业保险 | 见第 5 节 | 待开发 |
| ③ 用户上传 | 任何保单 | 和 ② 共用提取流程，也对应“学校 waiver 审核”的场景 | 待开发 |
| ④ 人工录入 | 种子数据、标准答案 | 人对照 PDF 填写。**不能由 Claude 或 Codex 代劳**，否则就不是 AMD 模型产出的数据 | 待做 |

⚠️ 大部分美国医疗保险都必须提供格式统一的 **SBC（Summary of Benefits and Coverage）**，读取会更稳定。部分留学生商业保险可能不受这条规定约束，需要查证。

## 5. 深度搜索

目标是**补齐一张固定的字段清单**，而不是“找到某个 PDF”。不计时间成本。

### 拆成三步
1. **找候选计划**（目标是不漏掉）：从学校 waiver 页面、多组关键词的搜索、已知计划清单中收集，合并去重。被多个来源找到的计划，可信度更高。
2. **拿到官方文件**（目标是拿到对的文件）：按下面的顺序尝试，前一个成功就停：
   1. 用搜索 API 限定网站和文件类型，加上计划名、“schedule of benefits”、年份
   2. 列出保险公司网站的所有链接，筛出 PDF
   3. 用 Playwright 打开网页逐层查找（最后的手段）
   
   **候选链接先由 Python 规则打分**：官方域名、标题关键词、当前年份加分；第三方网站、旧年份减分。只把前 3 名交给模型做选择题。
3. **验证**：计划名、年份、是否面向留学生、是否有 Schedule of Benefits，都由程序检查。不通过就退回第 2 步，换下一个候选。

### 由“还缺什么”来驱动
每读完一个来源，Python 检查清单里还缺哪些字段，再针对缺的字段继续搜（例如保费常常在网页上，而不在 PDF 里）。每个字段都记录来源的可信度：正式保单 > 官方手册 > 官网页面 > 第三方（第三方只能作为线索）。

### 工具
- **搜索 API（Tavily）为主，Playwright 为辅。**
  - 由 Python 直接调用 API，不通过 MCP。
  - **关闭 Tavily 自带的 LLM 生成答案功能**（`include_answer`）。
  - ⚠️ 比赛规则是否允许使用 Tavily，需要确认。从公开信息看，规则只要求主 agent 使用 AMD 模型。
- 被网站拦截时（例如 Cloudflare 返回 403），**不去绕过**，把该网站标为“访问受限”，换一个来源。
- 运行位置：比赛期间在本机运行；上线时用 Docker 部署到 Linux 服务器。不需要虚拟机，也不需要 GPU。

### 衡量和迭代
标准答案：5–8 个已知计划，每个都有正确的 PDF 链接和年保费，由人整理。指标包括：**找到率、文件正确率、字段完整度、每个计划用了几步**。哪一步的分数低，就改哪一步。

### 比赛范围
只做 UCLA 一所学校：1 个 SHIP，再加 5–8 个留学生商业保险。演示前跑一遍并缓存结果；现场再实时跑一次，用进度窗口展示过程。

## 6. 在 AMD 上部署模型

- 平台：**AMD Developer Cloud**，单张 MI300X（192GB 显存），约 $1.99/小时。选 vLLM Quick Start 镜像，区域选 ATL1。
- ⚠️ 额度：新成员 $100，约 50 小时，以实际拿到的为准。**不用时一定要关机**；需要保留环境时先存快照。截止后评委访问演示网址时，模型服务器是否开着，需要提前规划；演示视频作为备份。
- 候选模型：
  - agent 和深度搜索：**Qwen3.5** 或 **gpt-oss-120b**，启动时打开 tool calling 参数。
  - 读保单：需要能看图的模型。⚠️ 需要查证上面的模型是否支持图片；如果不支持，就另外部署一个看图模型，192GB 显存可以同时跑两个。或者先用 `pdfplumber` 提取文字。
- 接入方式：代码通过 OpenAI 兼容接口（`base_url`）连接自己的 vLLM，见 issue #2。

## 7. 展示 AMD 的应用（Application of Technology）

| 内容 | 必要性 | 可以展示的数字 |
| --- | --- | --- |
| 在 MI300X 上自部署 agent 模型和看图模型（一张卡跑两个） | 必须 | 显存占用、响应速度 |
| **在 GPU 上批量“编译”保单**：每份并行提取 3–5 次，结果不一致的标成需要复核 | 必须，这是最主要的 AMD 计算负载 | 每小时处理的保单数、每份成本、准确率 |
| 小规模 LoRA 微调：服务名称 → 25 个统一服务名称（`service_key`） | **可选，只在核心功能完成后做（第 5–6 天）** | 训练前后的准确率 |

关于训练：
- **训练数据必须经过人工核对**，不能用模型自己提取、未经核对的结果。
- 不训练“懂保险的大模型”：数据、时间、预算都不够。
- 长期来看，人工核对过的目录数据本身就是将来微调的训练材料。

## 8. 前端交互

参考 `docs/research/hark-interaction-patterns.md`。只借鉴交互思路，界面由我们自己设计，不照搬代码或视觉设计。

- 对话中的**选择题和填空卡片**：
  - 选项由 Python 根据数据生成，固定带一个“不知道”选项。
  - 答案作为工具的返回结果交回 agent，按字段记录来源。
  - 用户填的数字直接交给计算器。
- **确认卡片**：在计算前展示模型理解的服务、网络、金额，用户确认后才计算。
- **dashboard 用固定组件**：agent 只决定显示哪些组件，数字由后端填写。后端通过 SSE 推送更新。
- **深度搜索进度窗口**：每个网站一张卡片，显示当前步骤；自动跟随正在工作的卡片；完成后显示总览；用户可以点击查看。第一版不做复杂动画。
