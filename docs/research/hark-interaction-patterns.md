# Hark 前端交互模式研究

- 研究对象：`https://hark.com/chat`（2026-10-12，用户本人登录的浏览器页面）
- 方法：用 REA 被动观察页面结构，并对抓到的前端代码做静态分析。全程不点击、不修改页面，也不执行页面代码。
- 范围：只研究交互**模式**，用于设计我们自己的实现。没有复制任何代码、样式或素材；用户页面上的个人内容也没有记录。

证据编号：页面结构 `ev_5e60b8dc…`，脚本抓取 `ev_8e26216e…`，脚本导出 `ev_aef421e5…`。

区分方式：**观察到**是指在代码里直接看到的；**推断**是指根据代码结构推测的。

---

## 1. 对话状态由服务端推送“补丁”拼出来（观察到）

- 前端用 **SSE**（`EventSource`）长连接接收服务端推送，断线后会自动重连并逐步拉长重试间隔。
- 服务端推送的不是整段文字，而是一串**补丁操作**，每个操作都带序号（`patchSeq`）：
  - `entry_add`：在时间线上加一个条目，用 `afterId` 指定插在哪一条后面
  - `message_update`：更新某条消息的部分字段，比如流式输出中的文字和 `isStreaming`
  - `tool_add` / `tool_update`：在消息下挂一个工具调用，或更新它的状态
  - `panel_add` / `panel_update` / `panel_remove`：增删改旁边的面板
  - `ask_update`、`window_update` 等
- 对话的状态分成几张表：`messages`、`windows`（面板窗口）、`asks`（向用户的提问），再加一个 `log` 来决定它们在时间线上的顺序。

**对我们的启发：** 这正好对应 report JSON 里“`inputs` 可以修改、`results` 由 Python 算”的设计。后端每次重新计算后，推送“改了哪些字段”的补丁，前端只需合并补丁，不用整页重画。

## 2. “向用户提问”是一个状态为“等待输入”的工具调用（观察到）

- agent 调用工具时，工具调用上可以带一个 `userInputRequest`，这时它的状态变成 `waiting_for_input`。
- `userInputRequest` 里有这些字段：`requestId`、`prompt`（问题文字）、`choices`（选项，可以没有）、`displayHint`（显示方式）。
- 用户回答后，系统会记录一个 `userInputResolution`。
- 提问也会以 `ask` 条目出现在对话时间线上，和普通消息并列。

**对我们的启发：** 和我们设想的 `ask_user` 工具一致。提问不是 agent 回复里的一段文字，而是一个**有编号、有状态的结构化对象**。这样关卡 3 就能检查“有没有发出提问”，而不只是检查回复里有没有问号。

## 3. 选择题卡片（观察到）

- `choices` 不为空时，前端显示一张**选项卡片**；为空时只显示问题文字。
- 卡片的结构：标题、正文、下方附加区域，再加一个**“拒绝或关闭”按钮**（用户可以不回答）。
- 交互细节：
  - 点击选项后，卡片进入“提交中”状态，**按钮全部禁用**，防止重复提交。
  - 提交失败时，**错误直接显示在卡片上**，可以重试。
  - 选项的序号不合法时，会在前端拦下并提示。
  - 卡片可以折叠，折叠后显示一行摘要。
- 提交答案：前端向 **`/api/messages/tool-response`** 发送 `dispatchId`（对应哪个工具调用）、`requestId`（对应哪个提问）和选中的值。agent 收到后，就把它当作这个工具调用的返回结果。
- 埋点会记录选了第几个选项、一共有几个选项、提交花了多久、结果是成功还是失败。

**对我们的启发：**
- 我们的确认卡片和选择题卡片可以照这个结构来做：问题 + 选项 + 拒绝按钮 + 提交中状态 + 卡片内显示错误。
- **答案作为工具的返回结果交回给 agent**，而不是当作一条新的用户消息。这样每个答案都明确对应某一个问题、某一个字段，hook 就可以按字段记录来源。

## 4. 填空表单（观察到，只用于敏感信息）

- 填空用的是另一种表单组件，有字段值、字段错误、提交中、返回、关闭这几种状态。
- 在 hark 里，这类表单主要用来**填写敏感信息**：登录凭据、API key、一次性验证码、银行卡号。另外还有一种“手机端审批”，状态是等待外部操作。
- 敏感字段会交给一个独立的“保险箱”组件处理（`vault`），**填写的内容不经过 agent**（推断）。
- 表单的结果分两个阶段：保存和回复，每个阶段都可能成功或失败，都会单独记录。

**对我们的启发：** 我们的 allowed amount、剩余 deductible 这类数字填空，可以复用“字段 + 字段错误 + 提交中”的结构。“内容不经过 agent”这个思路也可以借鉴：**用户填的数字直接交给 Python 计算器，不让模型转述**，模型就没有机会改写数字。

## 5. 对话旁边的面板（观察到）

- `windows` 里可以有多个 `panels`，由服务端用补丁增删改。agent 的工作过程（例如浏览器截图）也显示在面板里，可以最小化。
- 界面上有“新建面板”和“面板菜单”按钮。

**对我们的启发：** 这就是 `PRODUCT.md` 里“Dashboard + Bot”的布局。dashboard 组件可以作为面板，由后端推送补丁来更新。agent 只决定“加哪个面板”，面板里的数据由后端填写，这和我们定的“agent 只选组件，数字由 Python 填”一致。

## 5b. agent 工作小窗口（观察到）

对话旁边那个能看到 agent 在浏览网页、可以最小化的小窗口，是 agent 工作过程的“直播窗口”。

**内容：每个工具调用是一张卡片**
- 只要工具调用带画面，就生成一张卡片。卡片类型有：浏览器、终端（shell）、写代码、地图、文件、代码、图片。
- 浏览器卡片显示的是**每一步的截图**（按截图编号更新）加上当前步骤的说明文字，不是实时视频（推断）。面板更新里带有光标位置，所以截图上可以叠加光标。
- 同一类型的卡片会叠在一起，可以把最上面那张翻到后面。

**“镜头”自动跟随正在工作的卡片**
- 前端有一个状态机来决定当前显示哪张卡片：
  - 新工具开始：推入、停顿、放大
  - 切换到已有卡片：平移、停顿、放大
  - 然后停留一会儿，再退出停留
- 同时有好几个工具在跑时，用一个队列**逐个展示**：中间的快速带过，最后一个停留得久一些。
- 怎么判断卡片“有变化、值得看一眼”，每种卡片的规则不同：
  - 浏览器：当前步骤变了
  - 终端：命令数或输出长度变了
  - 写代码：阶段或迭代次数变了
  - 其他：截图变了
- **卡片变成“等待用户输入”时，一定会被切到前面**，让用户马上看到 agent 在等他。

**全部完成后显示总览**
- 所有工具都结束后：只有 1 张卡片就停在那一张上，有多张就缩小成**总览网格**，一次看到全部结果。
- 每张卡片显示状态：完成、失败、取消、中断、等待输入。

**用户可以接管**
- 点击某张卡片，进入专注模式，**暂停自动跟随**。
- 用左右箭头翻看，或者缩小成总览。
- 点“恢复实时跟随”，就回到自动跟随。
- 整个窗口可以最小化。

**对我们的启发：** 这正是**深度搜索**需要的进度展示。

| hark 的做法 | 深度搜索的做法 |
| --- | --- |
| 每个工具调用一张卡片 | 每个候选计划或网站一张卡片，显示最新截图和当前步骤，比如“正在 X 保险的网站找保单 PDF” |
| 镜头自动跟随正在工作的卡片 | 自动显示 agent 正在处理的网站 |
| 等待输入的卡片自动切到前面 | 遇到验证码、需要登录、或者需要用户确认时，卡片切到前面，并弹出 `ask_user` 卡片 |
| 完成后显示总览网格 | 搜索结束后显示所有计划：已找到、已验证、失败（附原因） |
| 用户点击卡片后暂停跟随 | 用户可以点开某个网站，看 agent 的完整操作记录 |

我们不需要 hark 那么复杂的动画。第一版做到“卡片列表 + 自动跟随 + 完成后总览 + 点击查看”就够了。截图只是给用户看的；模型读的仍然是网页的文字结构（见深度搜索的设计）。

## 6. 其他

- 卡片可以作为“回复对象”（`replyTarget`），用户可以针对某一张卡片继续提问。对应 `PRODUCT.md` 里“点击 dashboard 条目，bot 直接解释这一条”。
- 语音输入用的是单独的 WebSocket，和对话的数据流分开。

## 我们怎么做（对照表）

| hark 的做法 | 我们的做法 |
| --- | --- |
| SSE + 带序号的补丁操作 | 后端用 SSE 推送 report JSON 的补丁；前端合并补丁后重新渲染 |
| 工具调用带 `userInputRequest`，状态为 `waiting_for_input` | `ask_user` 工具：模型只给出字段名，Python 生成选项和说明，状态为等待输入 |
| `choices` 选项卡片 + 拒绝按钮 | 选项来自计划 JSON（比如 `network_tiers`、`service_key`），**固定带一个“不知道”选项** |
| 答案通过 `tool-response` 作为工具结果交回 | 答案按字段交回，并记录 `source: "user_form"`；hook 按字段检查来源 |
| 敏感表单不经过 agent | 用户填的数字直接交给计算器，模型拿不到原始输入、也改不了 |
| 面板由补丁增删改 | dashboard 组件作为面板；agent 只选组件，数据由后端填写 |
| 卡片可以作为回复对象 | 用户可以针对 dashboard 上的某一项追问 |

## 局限

- **只做了静态分析，没有观察到实际的网络通信。** 补丁的具体数据格式、SSE 消息的结构，是从前端处理代码推断出来的。
- 研究时的那段对话里**没有出现选择题卡片**，所以卡片的视觉样式没有看到。上面的结论来自代码。
- 代码是打包压缩过的，变量名都没有意义。字段名（`userInputRequest`、`choices` 等）是代码里实际出现的字符串，可信度比较高。
