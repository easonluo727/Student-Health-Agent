# Branch A × MRF rate integration: decisions and open items

Scope: an overlay that connects Branch A (policy PDF rules, `workflow/`) to the MRF allowed-amount data
(`scripts/mrf/`, `data/mrf/`). Every change lives in `branch-a-mrf-integration/`. No original file was edited, and
nothing is merged back automatically. The baseline is described in `baseline/manifest.json`.

## Protecting the existing implementation

- **Starting point.** Branch `mrf-expand` at commit `3698b7d`. `git status --porcelain --untracked-files=all`
  printed nothing and the stash was empty, so there were no uncommitted changes to preserve. Gitignored local
  artifacts (`data/mrf/rates.sqlite`, `la_npis.csv`, `raw/`, `work/`) are listed in the manifest and are
  referenced by path only. They are never copied.
- **Baseline.** The four files this overlay adapts (`import_policy.py`, `agent_tools.py`, `agent.py`,
  `guards.py`) are snapshotted under `baseline/files/`. The manifest records their git blobs and sha256.
- **Proof the originals are untouched.** `tests/test_real_data_and_baseline.py` checks the originals and data
  inputs against those hashes, checks that `git status` is empty for every protected path, and runs the
  original `tests/` suite.

## Design decisions

1. **Wrap instead of copy.** Overlay modules have new names (`branch_a_tools`, `quote_guards`,
   `branch_a_agent`, `policy_import_v2`). They import the originals from their real locations: `PolicyTools`,
   `ConversationGuard`, the pure `calculate_cost`, and `scripts/mrf/allowed.py`. Nothing original is shadowed.
   `overlay_config.py` sets the import order, and every data path can be overridden through `BRANCH_A_*`
   environment variables.
2. **Two import outputs.** `policy_import_v2.py` writes three files:
   - `policy_metadata.json`: issuer, plan name and IDs, region, coverage dates, and network names as
     printed, each with its source page.
   - `benefit_rules.json` (`benefit_rule.v2`): the original rule fields plus `rule_key`, `source_file`,
     `source_page` and `review_status`. The schema forbids rate fields in a rule.
   - `policy_mrf_map.pending.json`: always `pending_review`, with `mrf_plan_key` and `mrf_network` set to
     null.

   The two kinds of page can come from different PDFs. Python validates page numbers, dates and IDs, and drops
   any value whose page lies outside the requested range. The PDF's "in-network"/"out-of-network" labels are
   treated as benefit categories, never as MRF networks.
3. **AMD-only LLM.** `AMDExtractor` and `amd_client()` require `AMD_API_BASE_URL`, `AMD_API_KEY` and
   `AMD_MODEL`, and refuse `api.openai.com`. There is no default and no fallback. The `openai` package is
   used only as the client library. Outputs are constrained with `response_format: json_schema`. The agent
   uses chat completions, because the original Responses-API features (`reasoning.encrypted_content`) are
   OpenAI-specific.
4. **Explicit, versioned mappings.**
   - `data/policy_mrf_map.v1.json` maps a policy plan and network category to one MRF `plan_key` and an
     exact `network_name`. When a plan was imported without a network filter (L.A. Care), `mrf_network` is
     null and the profile's market label is used.
   - `data/service_rate_map.v1.json` maps a plan, service, setting and network category to options. An
     option is either an A encounter or a list of B components, and each option records its clarification
     question, review status and source.
   - Only entries marked `verified` resolve. Pending, missing or duplicate entries return an unresolved
     status.
5. **Controlled encounter labels.** Table A in the CSV keys encounters by display label, while
   `encounters.csv` uses stable keys. `data/encounter_labels.v1.json` is generated by
   `build_encounter_labels.py` from `encounters.csv`. The resolver checks it against the CSV on load, and a
   test checks that it is current. There is no fuzzy matching.
6. **When an A total is allowed.** An A encounter total is used only if the mapping names the paying benefit
   for every component of the encounter, and all of them are the rule's own benefit. Otherwise the resolver
   returns `mapping_invalid` and the B option must be used. A and B are never combined in one estimate,
   because each quote has a single `rate_table`.
7. **B component matching.** Components match exactly on plan, network, code, `billing_class` and the exact
   POS string of table B. The CSV does not store the modifier rule, so it is re-derived with the same rule
   that `report.py` uses. If the requested rule differs, the result is `no_match`. If any required
   component is unresolved, there is no total. Optional components can be skipped and are listed as such.
8. **Provider-specific rates come only from SQLite.** NPI lookups go through `scripts/mrf/allowed.component`
   with `npi` set, and are accepted only when the result's basis is `provider_rate`. If the database is
   missing, the status is `no_data_source`. If the NPI has no rate, the status is
   `provider_rate_unavailable`; there is never a silent aggregate fallback. CSV quotes are always
   `aggregate=true, provider_specific=false`, and `n_providers` is reported as a count.
9. **Fail closed.** A quote is usable only when its status is `success` or `estimated` and its amount is
   finite and greater than 0. Every other status has `allowed_amount=null`. There is no fallback across
   insurer, network, code, class or POS. Out-of-network rules are never priced with in-network MRF rates.
   The MRF snapshot date is the latest file date. It is stale if it is older than 62 days (two monthly
   cycles) or later than `as_of`, and it is reported separately from the user's `service_date`.
10. **Quote provenance.**
    - `QuoteStore` keeps every quote under a random `quote_id`. It hands out copies and checks a digest of
      each stored quote.
    - `calculate_with_quote` accepts only `rule_id`, `quote_id` and `remaining_deductible`, so the model
      cannot pass an amount, network, code, provider or source.
    - The quote must belong to the same plan, service, setting and network category as the rule being
      calculated.
    - `QuoteGuard` still requires `remaining_deductible`, any NPI, and manual allowed amounts to come from
      the user. It also blocks choosing among several rate options until a `needs_clarification` result has
      been followed by a new user message.
11. **Per-component costing.** Each B component is costed with the pure `calculate_cost`, through the original
    `PolicyTools.calculate_estimate`, under the single benefit rule that matches its benefit service, setting
    and network category. Python consumes the remaining deductible in component order and sums the
    components. A missing or ambiguous rule for any component means no total.
12. **Manual fallback.** `calculate_estimate` is unchanged apart from the label
    `allowed_amount_source: "user_provided"`. MRF results are labeled `"mrf_quote"`.

## Open items: mappings that need a human

Run `python overlay/workflow/list_pending_mappings.py` for the live list. As of this commit:

| Mapping | Status | What a human must decide |
|---|---|---|
| `prime_100` in-network → MRF plan/network | pending, no candidate | Which insurer issues `prime_100`? The archived rules have no issuer, network name or page. |
| `prime_100` out-of-network → MRF | pending | Same. Note that MRF in-network rates never price out-of-network rules. |
| `consultant physician fees` → office visit options | pending | Is this benefit the right one for 99213, 99203 and 99214, and is 99214 the right code for a specialist follow-up? |
| `laboratory procedures` → labs, STI and urine tests (B) | pending | Confirm the lab bundles and that every test is paid under this benefit. |
| `diagnostic x-ray services` → chest X-ray, knee MRI, back MRI | pending | Does MRI fall under "diagnostic x-ray services" or under a separate imaging benefit? |
| `medical emergency expenses` → ER by component | pending | Confirm that the ER physician and facility are paid under this benefit and the X-ray under diagnostic X-ray. If the copay waiver or other conditions apply, the rule is `needs_review`. |
| `injections` → flu shot | pending | Is the vaccine priced under injections or under preventive care? The administration fee is not included. |
| UC SHIP and other real plans | not imported | Import the actual PDFs with `policy_import_v2.py`. Then confirm `policy_mrf_map`, for example UC SHIP → `anthem_ca_prudent_buyer_ppo` / `CA PPO PRUDENT BUYER`, which the product notes state but no PDF in this repository proves. |
| Billing codes and encounters (`data/mrf/*.csv`) | the original 16 codes and 18 encounters are unverified | This was already open in PR #3 and PR #4. |

The draft mappings were written from `encounters.csv` by the coding assistant. Under `AGENTS.md`, data
written by a coding assistant must not be trusted as catalog data, so every draft stays `pending_review` and
the resolver refuses it until a person sets `verified` and `reviewed_by`.

## Known limits

- Archived `prime_100` rules have `setting = null` and percentages in 0–1 units. The original calculator
  returns `needs_review` for them, and the overlay keeps that behavior.
- Report cells are medians across providers. They are negotiated rates, not final allowed amounts.
- `policy_import_v2.py` has been tested with an injected fake extractor. It has not been run against a real
  AMD endpoint here, because no AMD credentials are available in this environment.
